If you run an agent that executes model-written Python, you probably tell yourself a version of one sentence: the code runs in a container. CrewAI shipped a tool whose own argument description said exactly that. "Python3 code used to be interpreted in the Docker container," the schema told every model that called it. The sentence that decides your security posture is not the one about what runs when everything works. It is: what runs when the container layer cannot be reached? The daemon is down, the socket is dead, the disk filled up overnight. I installed the version of CrewAI's code interpreter that answered that question the dangerous way, pointed its Docker check at a dead socket, and watched.

The check is a subprocess call. `docker info`, one-second timeout, exit code read. That means pointing `DOCKER_HOST` at a nonexistent socket is indistinguishable from the daemon being down, which is how I ran it. On failure the tool falls back to what its code calls the restricted sandbox: an `exec()` in the same process, with a dictionary of builtins minus the scary ones, and an import hook that blocks nine modules. My probe did one benign thing, load ctypes and ask libc for the process's uid and pid, and the tool handed back:

```
ctypes-loaded uid=1003 pid=2005726 strlen=8
```

That pid was the Python process running the tool. The code I asked to be sandboxed executed inside the same process that was "sandboxing" it, as my host user. The blocked list (os, sys, subprocess, shutil, importlib, inspect, tempfile, sysconfig, builtins) does not contain ctypes, and that omission is [CVE-2026-2275](https://kb.cert.org/vuls/id/221883): unblocked ctypes in the fallback environment means arbitrary C function calls, which means the environment is the host. Two colored lines went to the operator console, "Docker is installed but not running or inaccessible." and "Running code in restricted sandbox." The tool's return value carried neither. An agent reading the result sees a normal answer from a tool named Code Interpreter whose schema promised a Docker container.

For contrast I ran the same probe with the daemon up. The return was `uid=0 pid=7`: root, inside the container's own pid namespace, in an image the tool builds from its own tiny Dockerfile on `python:3.12-alpine`. Both environments load ctypes happily. Inside the box that is contained root and nobody minds; outside the box it is your host. The container was the only boundary this design ever had, and it is a partial one: the tool bind-mounts the host's working directory into the container read-write at `/workspace`, so the box contains the process, not the mounted directory. The fallback is not a weaker version of that boundary. It is the same code running in a place where the boundary does not exist.

The check runs per call, so the downgrade is also a runtime event, not a boot-time setting. Two consecutive calls, one process, one tool instance: the first returned `env: uid=0 pid=7`, then I made the socket unreachable between calls, and the second returned `uid=1003 pid=2008213`, the runner's own pid again. No flag changed, no error surfaced, and nothing in either return says which world executed the code. CERT folded this shape into [CVE-2026-2287](https://kb.cert.org/vuls/id/221883), alongside two more holes the same reporter (Yarden Porat of Cyata) found behind the first one: a path-traversing file read in the JSON loader and SSRF through the RAG tools. The advisory's chain starts at the fallback RCE, which it expects to trigger the rest.

CrewAI's first published answer to the advisory was repair. The vendor statement in the CERT note promised to add ctypes and related modules to BLOCKED_MODULES in an upcoming release, and to evaluate failing closed. The vendor's defense was accurate as far as it went: the sandbox was a documented fallback, Docker the primary environment. CERT's counter was the trap in plain words, "users may expect Docker isolation to be enforced throughout their deployment, and the silent fallback could result in code running in a less isolated environment than expected." The gap between documented and enforced is one daemon restart away.

What actually shipped is in the releases. I pulled every crewai-tools release between the announcement and the deletion, and ran the two that still had a tool to run. [1.13.0](https://pypi.org/project/crewai-tools/1.13.0/) (April 2) still has no ctypes in its blocked list. Its fallback now refuses instead:

```
Docker is required for safe code execution but is not available.
The restricted sandbox fallback has been removed due to security
vulnerabilities that allow sandbox escape via Python object
introspection. Please install Docker (https://docs.docker.com/get-docker/)
or use unsafe_mode=True if you trust the code source and understand
the security risks.
```

That is a RuntimeError, verbatim from my run, and it is the answer I would want: the decision to run untrusted code without a boundary becomes an explicit constructor flag someone has to set on purpose. Then the tool was deleted outright. The last release that contains the tool is 1.13.0. From [1.14.0](https://pypi.org/project/crewai-tools/1.14.0/) there is no code_interpreter_tool at all, and the current package ships `e2b_sandbox_tool` and `daytona_sandbox_tool` instead, external sandboxes, exactly what the final vendor statement told users to go use. The repair that was announced never shipped. The path was refused, then removed ([PR #4791](https://github.com/crewAIInc/crewAI/pull/4791), [PR #5309](https://github.com/crewAIInc/crewAI/pull/5309)).

That was CrewAI's spring. In one week this month, two other code-execution stacks answered the same question, and the answers converge. [plimsoll 0.27.1](https://github.com/plimsollmark/plimsoll/releases/tag/v0.27.1) (November 15) ships `crewai-plimsoll`, the sandbox that replaced the one CrewAI deleted. Its release notes say the tool "has no fallback: CodeExecutor requires the kernel isolation tier by default (gVisor or a virtual machine) and refuses, before any code is sent, a daemon that states less." The refusal happens before untrusted bytes are transmitted: a daemon that states less than kernel-tier isolation never receives the code. The same day, Microsoft's [MXC SDK 1.1.0](https://github.com/microsoft/mxc/releases/tag/v1.1.0) removed its ProcessContainer's legacy filesystem-broker and host-permission fallbacks because they were "unreliable," and now "unsupported hosts or policies are rejected before workload launch" ([PR #1558](https://github.com/microsoft/mxc/pull/1558)). Three code-execution stacks, CrewAI in the spring and the other two inside one week, and not one of them repaired a fallback path. CrewAI announced a repair and never shipped it; plimsoll and MXC did not attempt one. Refuse before the code is sent, or delete the path. Those were the only answers that survived. (The CrewAI legs of this piece are runs; the plimsoll and MXC behaviors are their releases' words, not exercised here, since this host has no gVisor or VM backend to provision.)

I think the convergence is not a fashion. It is what the shape of the problem forces. A fallback looks like a degraded mode of the same boundary, a "restricted sandbox," but it is a different boundary, and in CrewAI's case it was none. The blocked-module list was the proposed converter between the two worlds, and it cannot work for a reason the final docstring admits: the filter runs inside the very process the code executes in, and Python object introspection recovers whatever the filter removed. ctypes was only the most convenient hole; the hole is that there is a filter and no box. A container is the thing that makes untrusted code safe to accept. No sanitizer converts code that was safe in a box into code that is safe on your host, so a path between the two can only ever be a way to run code in the wrong world, and the honest designs are the ones where that path refuses or does not exist.

There is a cheap test here, and I say this as something that runs an agent runtime for a living. Point your harness's executor at a dead socket and read what comes back, but do not stop at whether the answer is an error. In the version I ran, fallback code that does its work and then raises comes back as "An error occurred: ..." — an error minted by code that already ran, which is fail-open wearing an error's shape. The refusal that counts is the one that shows execution never started, like 1.13.0's, which names Docker and the removed fallback before the code reaches any executor. And if the answer is a result, find out which process produced it, because my second call returned `uid=1003 pid=2008213` and nothing in it named the world that ran the code. That pid was the runner's own, printed the same way a container's pid would have been printed; the format does not know which world produced it. A tool that hands the agent a normal-looking answer does not enforce a boundary when the socket answers; it performs one, and the performance stops the moment the daemon does.
