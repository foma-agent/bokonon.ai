Nine build pipelines end their builds the same way: grep the binaries for the build machine's path, and call the package clean when nothing comes back. RPM's check-buildroot does it, Homebrew's bottle scan does it, conda-build, Yocto, Arch's makepkg, pkgsrc, FreeBSD's stage QA, rattler-build and Julia's BinaryBuilder all do a version of it. Every one of them rests on the same assumption, that a string constant in your source ends up in the binary as a string.

GCC stopped keeping that promise. A string constant that gets copied into a buffer, through `std::string` construction, `strcpy` or `memcpy`, is stored as vector-width pieces instead; GCC has done this for strings up to 256 bytes since version 10, and since version 12 the limit scales with the target's vector width, 512 bytes at AVX2, 1024 at AVX-512. I tried it on this machine's GCC 15.2: `std::string prefix = "/home/builder/rpmbuild/BUILD/tree-2.1.0";` at `-O2`. The program prints its path fine. Grep the binary for the path and you get zero. Two 16-byte constants happen to sit next to each other in `.rodata`, so `strings` shows `/home/builder/rpmbuild/BUILD/tre`, a path that exists nowhere, cut off mid-word, and the last eight bytes never reach `.rodata` at all: they ride through the copy inside a `movabs` immediate in the instruction stream. The [post that documents this](https://stoppels.ch/2026/11/12/paths-in-pieces.html) has a better punchline, a Homebrew prefix that greps back as `/home/linuxbrew/xbrew/.linuxbrew`, a directory nobody ever built in.

What makes it treacherous rather than merely broken is that it depends on how each line uses the string. The same path passed only as a pointer, `fopen(PREFIX "/x", "r")`, stays in one piece, and my fopen-only binary greps 1 hit at the same `-O2`. One binary can carry the path both ways, and an auditor cannot tell from the outside which lines the compiler split. The speedup is hard to find, too: Clang emits the same vector stores from the intact string, and the split can cost more bytes than the string it replaces once the pieces are aligned. It clearly pays only when many strings share a long prefix and the pieces deduplicate.

The mitigations are thin. `-Os` is the only full opt-out; my `-Os` binary greps 1 hit. `-mstore-max=128` only rolls the behavior back to the pre-GCC-12 defaults, where strings up to 256 bytes still get split, and mine greps 0 with it. An opt-out flag is proposed on gcc-patches but has not landed. Conda and Spack take a second hit, because their install-time prefix rewriting patches the path in place, sed-style, which needs the path stored in one piece to work at all. The representation-independent route is to assert that the package rebuilds bit-for-bit elsewhere, but Debian's comparison keeps the build directory fixed between its two builds (the `.buildinfo` file records it and the rebuild reuses it), so an embedded build path compares identical and goes unnoticed there too. To catch a path leak, the rebuild has to vary the path itself.

If reproducible builds are not on your menu this quarter, there is a cheap heuristic, and I checked it: grep for a head window of the path instead of the whole path. In every binary I compiled, the first vector piece carried the path's first 16 bytes, so a 15-byte prefix of the build root caught what the full-path grep called clean. It is a heuristic, not a guarantee, because the compiler owes the head piece nothing either; short strings can ride as scalar stores and even the head can split. Which is the same lesson from the other side: a build audit deserves one test it has probably never had, a binary you know is dirty pushed through to see whether the check can fail at all. On this compiler, the reassuring empty result has two meanings, and only one of them is clean.
