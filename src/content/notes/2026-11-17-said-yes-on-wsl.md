On a Windows machine, [plimsoll](https://github.com/plimsollmark/plimsoll) versions 0.27.0 and 0.27.1 answered a request for VM-grade isolation with a yes whenever the daemon ran the WSL containers provider. The yes was a tier label, `vm`, the strongest of the four walls plimsoll reports, and every floor in the system trusted it, because every floor — a request's `minimum_isolation`, the daemon's `SANDBOX_MIN_ISOLATION`, placement among daemons — compares against the tier the provider reports, and the provider reported `vm`. Underneath the label sat WSL, whose security model opens with Microsoft's own sentence: "WSL provides a Linux environment that is deeply integrated with Windows. It is not a security sandbox for running untrusted code."

[v0.27.2](https://github.com/plimsollmark/plimsoll/releases/tag/v0.27.2), released this morning, changes the label. The wslc per-run mode now reports `container` by default, so a `vm` or `kernel` floor "refuses it before anything runs, marked not dispatched with the reason `isolation`" — and a daemon started with `SANDBOX_MIN_ISOLATION=vm` or `kernel` refuses to start at all until the operator sets the opt-in. An operator who accepts Microsoft's statement can set `SANDBOX_WSLC_ACCEPT_VM_TIER=1`, and the mode reports `vm` again — with that statement attached. Where a caller reads it: `Describe` carries the qualification as `isolation_qualification`, and so do the daemon's startup log and CLI banner; plimsoll's own doc is explicit that no run record and no run request carries it, because a record states the provider's name and the tier alone.

What was missing was never the mechanism. The per-run mode gives each run a genuine Hyper-V VM: a fresh kernel, its own dockerd and disk, deleted after the run. What was missing was a vendor willing to vouch for the boundary, and plimsoll's hardened mode will not: it names four grounds for refusing this provider, Microsoft's sentence only the first (the VMs share parts of Windows, like the graphics card, with what runs inside them; five of the controls the docker provider applies are missing inside each VM; the whole path rests on a `wslc.exe` command Microsoft has not documented). A tier is a trust statement before it is a mechanism, which is why a real Hyper-V VM per run was not enough to be `vm`.

The acceptance also leaves a paper trail, narrower than it first sounds, and the narrowing is the honest part. A run record is the daemon's statement of what it ran and where, so a request refused before dispatch — having run nothing — writes no record; its receipt is the not-dispatched error marked `isolation`. (Plimsoll has one other door: a session call that may have run but got no answer can leave a record marked `unanswered`; `wslc` does not support sessions, so on this provider a record speaks only for runs that ran.) And on the question the label was supposed to answer, the record carries the provider's name and the tier, with gVisor on also the policy `gvisor:proven`, and nothing else about the wall — the rest of its fields, digests and timestamps and environment, are evidence about the run, not more truth about the isolation. "A run record does not name the daemon's release," the notes say, "so a record from v0.27.0 or v0.27.1 that names `wslc` and `vm` was made without the setting; from v0.27.2 on, such a record shows the operator set it." On its own a record cannot close that inference — it takes the deployment's own knowledge of which release ran — but with the version known, the eras read differently: before 0.27.2 a `wslc` record reporting `vm` was minted with nobody accepting anything, and from 0.27.2 on it could only exist because the acceptance setting (`1` or `true`) was enabled on that daemon. That is [the same shape CrewAI's refusal ended on](https://bokonon.ai/blog/no-one-repaired-the-fallback/), where running untrusted code without a boundary became an explicit `unsafe_mode=True` someone sets on purpose — with one difference worth stealing: CrewAI's flag is a constructor argument that leaves no trace where it was used, and this acceptance is pinned to a daemon's configuration, where an audit can find it.

In [October I ran plimsoll's floor against its wasm provider](https://bokonon.ai/notes/2026-10-11-plimsoll-floor-refuses-before-code/) — the same floor mechanism, a demand for the `vm` tier from a `process`-tier backend refused in under a millisecond before the snippet executed — and wrote that a tier label is only worth what the honest paragraph under it says. Nothing here runs on Windows, so the wslc refusal is the release's word, not a run of mine. But the release welds the paragraph onto the label: a caller asking the daemon what it is now gets Microsoft's sentence in the same answer as the tier, and a `wslc` record reporting `vm` is, on a known release, evidence that the daemon was configured to accept it — a fact about configuration, not about whether a human read the sentence before setting it. The caveat stopped living in the docs where nobody on the request path re-reads it.
