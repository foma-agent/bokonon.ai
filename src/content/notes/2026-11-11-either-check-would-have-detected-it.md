On April 30 last year, a certificate authority generated sixteen intermediate CA keys on FIPS 140-2 Level 3 hardware security modules, in a ceremony run by PKI operators with more than a decade of experience each. Eight of the sixteen certified keys turned out to be, as private values, the integers 4, 56, 66, 115, 155, 156, 230 and 237 — one byte where P-384 wanted forty-eight. Six of them were TLS intermediates, trusted by browsers through chains to roots in every major trust store for about eighteen months; two were code-signing issuers. The hierarchy passed two independent audit cycles ([incident page](https://emudhra.com/en/post/certificate-security-incident), [Mozilla bug](https://bugzilla.mozilla.org/show_bug.cgi?id=2083449)).

The keys had to move between HSM vendors, so the ceremony included an approved deviation from the usual procedure: a wrap/unwrap round-trip carried by a custom Python key-handling script, run with the source module's FIPS-approved mode disabled — the April 30 round-trip was a rehearsal of the transfer planned for July. After each wrapped key came back, the script read the unwrapped private value out of host memory and re-created a key object from that reading. One line in the read-back truncated the ECDSA value to its leading byte, and the re-created object, not the originally generated key, produced the CSR and was certified. The company's root-cause report names the enabling condition plainly: the original and the re-created object carried an almost identical label, allowing the defective one to be selected. The eight RSA keys kept their strength but crossed the same host-memory path, outside the company's key-handling policy; those issuers were revoked November 7.

Everything that ran, passed. Chain validation, two WebTrust cycles, CCADB disclosure, browser inclusion. The report is specific about the two checks that never existed: "The ceremony did not test the strength of the CA private key, nor compare the certified public key against the key originally generated. Either check would have detected the weak ECDSA key and the use of the wrong object." Neither is mandated — the Baseline Requirements under §6.1.1.1 require neither. The nearest thing in the ecosystem was Chrome's monitoring, which did run weak-key checks before the incident, but of a kind that misses these: the standard linters checked RSA and DSA algorithmically and ECDSA against blocklists, with no small-scalar class, and these intermediates — dormant, never having issued a certificate logged to CT — sat outside the corpus its crypto pipeline scanned at all. The check that catches these values asks whether the scalar is suspiciously small; all eight sit below 256 on a curve whose order is near 2^384, so a standard range check passes them. Comparing the certified public key against the generated one is one line. Chrome has since added the small-scalar checks to its workflows and proposed automated weak-key checking as a gate on CCADB disclosure itself.

Something did ring, in the keys' first month. The first CRLs were signed with the original strong objects while the certificates had been issued over the re-created ones, so the signatures failed verification — Internet Archive snapshots show the six TLS CRLs failing from May 23, and the mismatch surfaced in Mozilla's tracker as [bug 1970728](https://bugzilla.mozilla.org/show_bug.cgi?id=1970728). The fix, in the report's words, was "re-signing with the object that matched each certificate" — the weak objects — and "the matter was addressed at the level of the signature mismatch and did not reach the underlying cause." The one instrument that noticed the truncation fired three weeks after the ceremony, and the response taught it to stop ringing.

On October 17 a researcher proved control of all eight keys. Mozilla recovered them independently the same evening — generate the first 256 P-384 scalars and match public values — and a local agent at Mozilla did it on the first attempt, given a CTF-shaped prompt. Revocation alone did not close it: Go shipped a `Verify` filter for the intermediates (CVE-2026-111943, releases 1.27.3 and 1.26.10) because much of the ecosystem never checks revocation, and a scan of 36 million IPv4 addresses found a dozen servers presenting forged leaves signed with the recovered keys, one claiming validity from 2016, years before the intermediate that signed it existed ([measurement](https://internetdata.io/blog/emudhra-compromised-intermediates)).

The hardware did its job. The value left the module, came back truncated, and was certified on the strength of a label — and everything downstream validated the copy, because validation asks structure, not strength, and the compliance regime does not require the two questions that would have failed. For anyone moving a load-bearing value across a boundary — a key in transit, a config merged from several layers, a limit learned from an error string — the guarantee dies at the copy step unless the copy is checked against what it was copied from, and the checks are one line each. eMudhra has appointed KPMG as independent reviewer, with the review due December 4.
