Gnomon's pitch to anyone handing an agent a production database: the agent gets its own branch of the real Postgres, every field it changes comes with a diff and a review, nothing it queues — emails, webhooks, payments — leaves before the merge, and because the database records the moment of every read, a replay returns exactly the rows the agent saw. I installed 1.0.1 on a stock Postgres 16 container and priced each promise, with a small orders-and-refunds schema standing in for the kind of business tables this is aimed at.

Three held, byte-clean. Replay: the agent on its branch read order 4182 as open at 480.00 and I captured the coordinate of that read through the run-record function (`gnomon.coordinate_text()` at the read — the same record their CLI drives, not the C-module read log); main then cancelled the order and zeroed the total; a fresh session reading at the captured coordinate returned the row exactly as the agent had seen it, matching md5 for md5. The history layer that answers this works on the plain-SQL install, no C module involved. The difference between "the agent said the invoice was open" and knowing it was is now a database query. Approval: a review records the branch head it covered — the reviewer approved one refund, the agent wrote a second on its branch, and the merge refused with "change request 1 was approved, but its branch changed after the approval." The default discards stale approvals rather than standing by them. Held outbox: a listener that was live the whole time got exactly one notification, delivered when the merge landed, carrying the row the agent had queued minutes earlier; the branch write itself produced nothing. Two smaller things worth knowing: an agent can ask for main by name and read it, and what the database refuses is the write ("permission denied for table orders"); and merges need no change request or approval until you turn `require_change_request` on — `done()` opens one for a person to look at, nothing more.

The fourth promise is the interesting one. A merge policy can say the agent's branch must not have "read a row that main has changed since," and that guard is what makes a review worth anything: it is the thing that stops a decision made on yesterday's state from landing today. On the plain-SQL install — the same objects RDS, Aurora and Supabase get through pg_tle, which cannot load the C module — no branch read is ever recorded. The one function that writes the read log is called only from the C module's query rewriter. So I staged the guard's own scenario: the agent read order 4183 as open at 75.50, main shipped it at 80.00, and the agent merged a 75.50 refund through an active `no_stale_reads` policy with zero violations. Main now holds an order shipped at 80.00 carrying a refund decided from a state that was already gone when it landed. The knob ships everywhere; its evidence ships almost nowhere.

Where the C module is installed, the docs still need one correction and one repair. `gnomon.use()` is documented to turn read tracking on, and does not — the tracking GUC defaults off and only an explicit set records a read. And on a fresh database the first branch's reads land in a broken window: the read log records the branch-base cutoff as the moment of the read, that coordinate sorts just before the table's tracking horizon, and the recorded read alone — no change on main needed — makes `stale_reads()`, `gnomon.done()` (so the agent cannot even submit its work for review), and the merge itself die with "no history of public.orders before it was tracked." Deleting the read-log row lets the merge through. I filed the crash and both smaller notes with a full reproduction: [gnomon issue 1](https://github.com/bitsinfra/gnomon/issues/1).

The decision-audit half is the one I would use, with one qualifier the review was right to force: replay at a captured coordinate is what I ran, and it worked on the plain-SQL install too — but "the database records the moment of every read" holds only where something does the recording. On the managed tier, per-run coordinates exist when the caller's tooling writes them (their CLI passes them to the run-record function), and the automatic per-read log does not exist at all. For business tables where "what did the agent actually see" is the first question after a bad write, a recorded coordinate answers it from the store rather than from the agent's own account — if you know which recording path your install has. Before relying on the stale-read guard, ask which install path you are on, because on the managed tier the guard has no input, and on a fresh self-hosted install it stands between your agent and its review as a crash. The maintainer has both receipts, with the exact commands.
