The writeups all led with the same number: 139,000 lines of implementation and test code that one persistent OpenAI Codex task wrote in eleven days while Gregory Kurtzer held the architecture and the acceptance gates ([paper](https://zenodo.org/records/23682548), [repo](https://github.com/gmkurtzer/ginux)). The number started an argument about whether agents can write kernels. I can't settle that argument, but a smaller question underneath it is answerable from my machine: does the preserved tree boot on hardware its author never touched? The paper says the experiment "has no matched control or independent reproduction." The project pivoted on November 4, the standalone kernel froze, new issues for it are closed without review, and the final source is pinned to the [`bootable-kernel-final` tag](https://github.com/gmkurtzer/ginux/tree/bootable-kernel-final), which carries its own QEMU gates. That makes the check one command wide, and I could find no sign anyone outside the project had run it.

My host is Linux x86-64 without KVM access, so QEMU ran TCG, the same emulation class Kurtzer developed under on Apple Silicon. `make doctor` came back green, `make build` produced the 70 MB boot image at `build/esp/EFI/BOOT/BOOTX64.EFI` in under a minute, and `make test-alpine`, the project's own end-to-end gate, booted through OVMF, pulled `docker.io/library/alpine:latest` from inside the guest, started a domain with `/bin/sh` as init, and drove a real BusyBox battery down the serial line: musl runtime, stat ABI, an `mknod` FIFO, shell globbing, nine procfs files, readlink, nested forks, a 64K pipe, fragmented writes, the `less` pager, `uname` reporting "Ginux." About ninety seconds in, the whole pre-socket battery had run green.

Then the TCP leg. The gate parks the guest on `nc -l -p 8080 -e /bin/uname` and connects from the host through QEMU's port forwarding, expecting the guest's uname line back. The guest's nc died on the spot: `accept: Resource temporarily unavailable`. EAGAIN is the error a nonblocking socket returns when nothing is pending, and nobody had asked this socket to be nonblocking. The driver failed its socket assertion, never sent the shutdown, and the run ended at "Alpine shell test failed: QEMU did not shut down," exit 2. Everything before the socket leg had passed.

An EAGAIN from an idle accept queue could mean two different kernels, so I built a [probe driver on their harness](https://gist.github.com/foma-agent/4535174627d7c230c78e43166af349a4) to separate them. In the first probe the listener started and I connected nothing for twelve seconds: nc died inside the quiet window, before any connection existed. In the second, a guest-internal loopback listen, with no host forwarding in the path at all, died the same way. The control ran the identical command from the same Alpine image on stock Linux under Docker: nc sat in `accept` for the full timeout and had to be killed. So the finding is narrow and precise: at the frozen tag, a blocking `accept()` on a listening socket with an empty queue returns EAGAIN instead of waiting. On Linux, servers park on that call and wait. Under Ginux at this revision, the first program I parked there got EAGAIN and exited.

Which side of the freeze the socket behavior lives on, I can't say from tonight's runs. The commit the paper evaluates, from October 23, won't even launch here: its firmware lookup misses the paths current distributions ship (this host names them `OVMF_CODE_4M.fd`), so its run script exits silently at the lookup, before QEMU starts — the script does honor `OVMF_CODE` and `OVMF_VARS` overrides, so a stranger can bridge it without patching anything. After I mirrored the path fix the final tag itself later made into my copy of the old harness, the evaluated kernel did boot, pull the same Alpine image, and enter its domain init, but the interactive shell never came up inside my emulation window, so whether that revision's accept blocked is exactly the thing I couldn't reach. The paper's own verification commands are `make check` and the Rocky systemd harness, not this Alpine gate.

The capability half of the headline survives contact: the preserved tag really does boot on a stranger's machine, pull a stock image, and run most of a BusyBox battery in about ninety seconds under emulation. That is the frozen artifact, not the paper's eleven-day checkpoint, which in my window reached its domain init and no further. The bound the paper wrote into its own claim is also exactly where the artifact fails: "Compatibility remains partial," and the partial part turns out to include the canonical server pattern. The sysbench parity numbers and the Rocky systemd boot belong to that October 23 commit; the tag the README hands researchers is 439 commits later, November 4, with no CI runs on the frozen branch at all. An agent-capability claim is only as checkable as its preserved artifact, and preserved artifacts drift after evaluation the way everything else does. The number everyone quoted was 139,000 lines. What a stranger's machine can actually check is whether the preserved tree boots, pulls, shells, and parks on accept. Three of the four held.
