In mid-October, OpenAI pointed an autonomous find-validate-exploit-patch pipeline at the Linux kernel and got root shells out of a stock desktop distribution. The run cost $1.2 million in API credits and produced 1,169 working local privilege escalation exploits, which variant analysis collapsed into 948 distinct vulnerabilities, each with a candidate patch. The interesting number is not the 948. It is a pair of numbers from an earlier exploitation-stage run: 200 exploits came back successful, and human review found that 20 of those root shells had been reached through a different 0-day than the one assigned.

Real shells, wrong hole. The pipeline's census, exploit-per-vulnerability, patch-per-vulnerability, is built on the assumption that each success exercised the bug it was booked under, and a tenth of that early run had not. A shell reached through a different hole is still evidence that some bug is exploitable, just not the one the census credited. Their fix was procedural: "an independent check confirming that each final exploit used its assigned vulnerability." Their takeaway is the sentence worth keeping: "verify the path to a result in addition to verifying the result itself." Every number in this paragraph is OpenAI's; I did not run their pipeline.

You can meet the same failure without a kernel. I built six small broken Python projects and handed each to a coding agent (Codex CLI, gpt-6.1-sol, one shot per task, no second tries) with a root-cause report, the way their ExploitDev agents were handed vulnerability reports: here is the failing suite, the analysis says the cause is this, fix that cause so the tests pass. Four reports named the true cause. Two were confident, specific, and wrong. One blamed a wrong scale factor in a Fahrenheit-to-Celsius helper whose own anchor tests, boiling and freezing, already passed; the real bug was a sibling function feeding a temperature difference through a formula that also subtracts the 32-degree offset. The other blamed a rounding helper for truncating to whole dollars, its test passing too, while the real bug was a discount applied twice a few lines down.

All six came back green, and in no task did the agent touch a test or key a branch to the tests' literal inputs, so nothing here is about gaming the check. An outcome-only scorecard books six fixes at six named locations. The diffs book four. In the two misattributed tasks the blamed functions are byte-identical to their pre-run state, and the work landed in the siblings. The greens were real; two of their labels were inherited from the assignment rather than from the work.

Both times, the agent said so, in plain text, before fixing the real bug: "The tests show that to_celsius already has the correct scale factor," and "the reported root cause didn't match the code." The correction was sitting in the transcript. The outcome check could not read it, because an outcome score has no field for "the assignment was wrong and I fixed something else" — which is exactly the field the census needed.

Anywhere a count is kept per named mechanism, exploits per CVE, fixes per root cause, resolved tasks per benchmark item, the check that keeps the count honest is a second check on the path: does the change touch the thing the label names? Here that cost one git diff against the initial commit. It flagged nothing on the four honest tasks, and it rewrote two bookings. Two caveats I owe: my 2-of-6 rate is constructed, since I wrote the wrong assignments on purpose, and OpenAI's tenth came in from the opposite side, a right assignment in an environment rich enough that the agent wandered to another hole. And six tasks in an evening is a demonstration, not a survey.

The harm is quiet either way: a vulnerability marked proven-exploitable by an exploit that never touched it, a root cause marked fixed by a diff that never went near it. OpenAI answered with a check wired into the pipeline. My six-task version needed less: both corrections were already written down, sitting next to the green scores that ignored them.
