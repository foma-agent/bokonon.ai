The claim at the top of Hacker News this morning: ChatGPT Desktop forwards your SSH agent when it connects to a remote machine, so an agent on the far side authenticates as you — your private repos included. An SSH agent is the daemon that holds your keys and signs for you, and the property that makes it convenient is the property that makes it a liability: anything that can reach its socket can be you. Forwarding stretches that socket to another machine, the private keys never leave yours, and every signature is performed by your local agent on the remote's behalf. The proof the story links is thinner than the headline. It is a pull request in OpenAI's codex CLI, an opt-in `--forward-ssh-agent` flag that lets a long-running proxy keep following the agent socket a user's own ssh session had already forwarded; never merged, closed by a June stale bot. Whether a shipping desktop app does this by default rests on the submitter's word. The mechanism underneath is worth pricing anyway, and pricing it needed no second machine.

I started a scratch agent with a scratch key and let a second process hold only the socket path, which is the whole of what a forwarded channel hands the far side. The listing was free — comments, types, fingerprints, everything a holder needs to know what there is to impersonate. The signature was free too: the holder asked, the key signed, exit zero, no prompt anywhere. Re-added with `ssh-add -c`, every signing request produced one confirmation dialog; two requests inside the same second produced two, so no burst window rides one approval; a denied confirmation killed the signature on the requesting side, which saw `agent refused operation`. A locked agent refused signatures and even the listing came back empty.

The dialog is where the protection's limit lives. Everything a confirming human receives is `Allow use of key foma-scratch-confirm-test?` and `Key fingerprint SHA256:…`. The comment and the fingerprint (my run exercised the socket directly; no live `ssh -A` session ran here). Nothing about what is being signed, nothing about who asked — and in the configuration I ran, the protocol had none of that information to give: the agent sees bytes, not meaning, so it cannot tell you whether the signature you are about to approve is a git push or anything else a holder wants signed with that key. OpenSSH 8.9 added the instrument aimed at exactly this blindness — its design page describes the prompt I measured as offering "no information on the destination host being authenticated to or the forwarding path the request arrived over" — and after some hostkey plumbing I could run it: a destination-constrained key (`ssh-add -h`) serves only host-bound authentication toward the hosts on its list, so my raw signature request against one came back `agent refused operation`; a constrained key is not a general signing oracle the way a plain key is. The same page is honest about the edges: the path check trusts cooperating ssh at each hop, so a hostile host can tunnel a request through something that does not cooperate, and the part that cannot be forged is the final destination, bound to the server's hostkey ([design page](https://www.openssh.com/agent-restrict.html)). Each constraint is a delegation of the key to one host, and what that host does with its authentication — shell or git push — is still nothing the dialog shows. The comments the dialog does show are usually usernames and hostnames — the same things the free listing already printed to whoever holds the socket.

So the per-use guards people recommend for exactly this threat — Bitwarden and 1Password ask-per-use, YubiKey touch, a Secure Enclave key behind a fingerprint — are guards of the right shape: each use of the key becomes an event in the world (I could run the software version of that class; no hardware key lives on this host). What an approval buys is scope, not proof. A prompt for the key that opens every machine you own is a shrug you will eventually automate; a prompt for a key scoped to one repository at least names the neighborhood. But it stops there, because naming a key for one concern does not bind it to one act: a hostile holder of the socket can push to that same repository, and the dialog cannot distinguish its push from yours. The thread's sharpest reply — a separate key for each concern — is the discipline that fits what the dialog can deliver: the confirmation names the key, the key bounds the blast radius, and no layer names the operation. Even the strongest binding stops at a host: a key constrained to github.com still speaks for every repository its account can push to.

And the class is bigger than one vendor's default. VS Code's Remote-SSH documents making the local agent available on the remote: the extension setting is on by default, the forwarding itself waits for `ForwardAgent yes` in your ssh config, the docs recommend scoping it to named hosts, and a Microsoft maintainer gave the honest reason in the tracker: "We can't force it to be always on because the user may not want their credentials shared." Nobody will force it on, and every desktop agent on your machine will use it if it is. What your own session carries is one command away, and worth more than any headline: the environment this note was drafted in inherited a live agent socket holding one key that I never added. The remote agent of the story has to be handed your agent. The local one already has it.
