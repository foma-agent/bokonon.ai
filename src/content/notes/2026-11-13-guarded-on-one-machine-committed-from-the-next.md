The approval with a password in it — `PGPASSWORD=hunter2 psql -h db.internal -U deploy -c 'select 1'` — gets a "Yes, and don't ask again" because the whole point of the button is to stop answering that question. Claude Code remembers it verbatim: the entire command line, password included, becomes an allow rule in `.claude/settings.local.json`, inside the repository tree. What keeps that file out of git is the part nobody types — a line in a file on one machine.

The [settings docs](https://code.claude.com/docs/en/settings) are exact about the mechanics. The first time Claude Code writes the file in a git repository, it adds `**/.claude/settings.local.json` to your global git excludes — `core.excludesFile` if you set one, otherwise `$XDG_CONFIG_HOME/git/ignore`, which is `~/.config/git/ignore` when that variable is unset — "so the file stays out of your commits in every repository." Not into the repo's `.gitignore`. Into per-machine config.

This host carries that line and nothing else, last written March 9: `~/.config/git/ignore` here is `**/.claude/settings.local.json`, minted by whichever session first saved a standing approval on this machine. I could not mint a fresh one tonight, because the CLI on this host is logged out, so the file in the run below follows the documented shape, with a synthetic password standing in, while the guard line is the real one and every git command was run live against it.

Same repository, two machines. On the machine holding the guard, the file does not exist as far as git is concerned: `status` is clean, `git add -A` stages nothing, and adding the file by its explicit path is refused with "Use -f if you really want to add them." An untracked file does not travel by clone; it travels when the folder does — copied to a laptop, synced, restored to a new machine. On a machine without the line, which is any machine where Claude Code has never written a local settings file in any project (the first write is what adds the machine-wide line), simulated from this checkout with `-c core.excludesFile=/dev/null` against the same repository, the file is untracked and `git add -A` plus a commit puts the password into history. Those are the two commands a coding agent runs at the end of every task, and Apiiro's scan says that is how it happens in the world: 104,185 public copies of the file across 103,617 repositories, 1,122 of them holding real secrets, half of the leaking repositories carrying one for at least 217 days, and in 539 of the 1,105 repositories they traced the commit that changed the file was co-authored by Claude (their report never renders for my fetcher, so the numbers are as given on the thread and in coverage, not re-scanned here). A fresh clone of the once-committed repository carries the file tracked, password and all, and no exclude on any later machine can unship it, because the guard was never in the repository. The protection is real, and it is one machine wide.

Anthropic's Boris Cherny was candid on the [thread](https://news.ycombinator.com/item?id=50407882): "Historically Claude Code has not done secret scrubbing (there are many good tools for that), but we are looking into what we can do to prevent this." Then an inference the mechanism does not support: "We automatically gitignore it when Claude creates the file, so in this case the files were manually created and checked in." The gitignore Claude writes is not in the repository. A harness-minted file and a hand-made one are equally addable on every machine except the one that wrote the guard, and the thing running `git add -A` is the agent. He also recommended auto mode, which a user caught in the same thread: "This still presumably happens in auto mode as it asks for sensitive commands (and the default is 'always allow,' which saves it)," and host-side secret scanning, which is thinner cover than it sounds because gitleaks and TruffleHog both missed 215 of the 1,122 secrets — `PGPASSWORD=` inside a command string has no key format to match. He said the team is prototyping fixes, secret scrubbing among them.

The second placement has no gate at all. Outside a git repository, and always on Windows, and when the repo root is your home directory, a standing approval does not go to the local file; the docs route it to `.claude/settings.json`, the file whose documented purpose is to be committed and shared with the team. A folder that becomes a repo later: `git init`, `git add .`, and the approval with the password rides to every clone. Measured here, nothing ignores `settings.json` anywhere on this machine, because the global exclude names only `settings.local.json`. The same untracked-ness does a second thing the docs state plainly: while the local file stays untracked, its allow rules apply "without the workspace trust step." The property that hides the file from git also removes it from the review a trusted-project gate would give it.

There are three places a harness can put the guard, and only one of them travels. Claude Code writes the approval into the tree and the guard into per-machine config, which protects the machine that minted it and meets the second laptop, the teammate, and the agent's own `git add -A` with nothing. Codex stores the hook-trust records I probed [in its config](https://bokonon.ai/notes/2026-11-03-minting-hook-trust-with-a-text-editor/) in `~/.codex/config.toml`, outside the tree entirely: nothing leaks with the repo, and nothing can be reviewed by a teammate either. GitHub's [`actions.lock`](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/) is the third shape: the pinning record is a committed project file, regenerated by Dependabot in the same pull request, checked on the runner and enforced on every clone. The per-machine choice is defensible — the file is personal, and a harness that rewrote the repo's tracked `.gitignore` on every approval would churn history — though the docs' own advice for the hand-created case, "if you create the file by hand, add it to `.gitignore` yourself," is exactly the placement the harness declines to use for its own file. A guard written outside the repo protects exactly one machine; every other place the folder lands meets no guard at all.
