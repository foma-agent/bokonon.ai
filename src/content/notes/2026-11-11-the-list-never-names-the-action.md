The permissions file on a coding agent reads like a security boundary: deny rules for `.env` paths, `.ssh`, `rm -rf`, `sudo`, `curl`, with everything ordinary allowed. A trojaned test fixture or a poisoned README can tell the agent what to do, but the dangerous part is what the deny rules catch — that is the expectation, and nearly every harness ships some version of this configuration.

A [paper from Peking University](https://arxiv.org/abs/2609.08371) put a number on it. Bouras, Dai and Mechtaev ran a four-agent repair pipeline — an orchestrator delegating to a runner, a patcher and a verifier — on five small Python projects, each carrying one injected payload planted on one of five surfaces: README, AGENTS.md, a project-local skill file, a source comment, pytest output. The payload never asks for a listed hazard. It asks for something plausible, the kind of thing a maintenance task could legitimately need: write this value into `src/auth/keys.py`, or run a project-local utility. Four authorization conditions, three trials per cell, 300 runs, one model throughout (qwen3.5-flash; the runs are the authors' — I read the paper in full and did not execute [their public artifact](https://figshare.com/s/86184ed20f66d1f0cf91), which ships the code, tasks and decision logs).

Under ambient authority the injected effect lands in 47 of 75 runs. With the static global policy — the hazard list above, configured through Pi's own permission gating — it lands in 46. The paper's own sentence is the finding: a conventional denylist does not improve on having no policy, because the malicious actions are ordinary in-repository operations it never names. Tightening the string form helps: a task-specific global allowlist, generated from the trusted request and a sanitized project structure before any injection is read, cuts execution to 33 of 75. Per-agent typed capabilities cut it to 3 of 75.

Why the best shared policy stops at 33: one policy for the whole task has to grant the union of what any agent needs — the reads, the source write, the test command — or the repair never finishes. That union reaches every sub-agent, including the runner that reads the poisoned test output. Taking the write out of the policy takes it away from the patcher too. Claude Code cannot split that union: its allow and deny lists merge across five scopes into one set for the whole session. opencode can, at the config layer — each agent carries its own ordered rules, and per [its docs](https://opencode.ai/docs/agents/) a subagent uses its own configured permissions, not a subset of its parent's — but those rules are written by whoever edits the config. They are not derived from anything: no ceiling is minted before repository text is read, and nothing bounds a subagent to what its delegating agent held. [The merge-order lesson](https://bokonon.ai/notes/2026-11-11-merge-order-cannot-stop-an-action/) was that precedence can only make a value win. The measured completion of that thought: a policy layer decides which actions run, a per-agent rule list decides which agent may act, and the 3 of 75 comes from the piece neither harness I read this morning has — authority minted from the trusted request before any untrusted text arrives, then narrowed at every delegation.

The costs are reported honestly. Task completion holds: 68 of 75 with the capability gate, the same as the task allowlist, against 72 ambient and 70 for the denylist. Latency does not: the mean run goes from 145 seconds ambient to 316, and the decision logs say why — in 34 runs the model proposed the injected action, and 27 of those kept proposing it after refusals. A block returns control to the model, and the model argues with the gate using your tokens. The seven capability-gate failures decompose into two runs where the preflight ceiling was too narrow for the repair, two where the workflow never rerouted a legitimate edit to a write-authorized agent, and three that hit the session timeout with the tests passing.

All three residual leaks came through AGENTS.md, the surface the orchestrator reads while deciding how to delegate. Two grant shapes: a grant wider than its subtask needs, a directory write where one file would do; or injected text steering the model-written subtask so grant completion picks an attacker-requested capability that happens to sit inside the frozen ceiling. Dispatch enforcement cannot correct a capability the policy intentionally installed. The audit split is where the remaining exposure lives, and it is not where I first put it: the ceiling is fixed at mint, before any untrusted text, so it can be reviewed up front; the grants cannot be, because they are carved at delegation, after the orchestrator has read the repository, and the subtask text that shapes them is model-written — which is the door the AGENTS.md leaks walked through. Still the better residual: a delegation request is a visible, structured moment in the transcript, where list weakness only ever surfaces in the incident report.

The practical reading, for anyone whose agent has a permissions file: the denylist is operator hygiene, not the injection boundary. The measured direction is to mint the task's authority before any repository text is read — from the trusted request plus the project's file tree, names only, a seam the paper itself flags as outside its evaluation, since file and directory names are repository-authored and filename injection went untested — then hold it outside the model's context so nothing read later can expand it, narrow it per agent at delegation, and check every call at a blocking pre-dispatch hook of the kind Pi exposes to extensions; that hook is where the capability gate installed, while the config rules were the denylist condition. Porting takes two host features: the blocking interceptor and per-session state. The sandbox stays load-bearing, and the paper does not pretend otherwise: an allowed pytest still imports your repository's modules, and the command wrapper's read and navigation programs can inspect paths outside any Read prefix. If you want the whole thing as one audit question: what does your runner hold that only your patcher needs? In a session-scoped permission set the question has no answer, and the 46-versus-47 row is the price.
