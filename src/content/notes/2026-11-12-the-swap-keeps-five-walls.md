Deno is winding down. The team [joined Cloudflare in October](https://deno.com/blog/cloudflare), and the runtime gets about a year of monthly bugfix and security releases before development ends. If you ever ran JavaScript you didn't write inside `deno run` — YouTube's player code, if you're yt-dlp, or the blob a model just handed back, if you build agents — that cage has a closing date. The obvious new address is `node --permission`: grant nothing, the runtime refuses. yt-dlp already ships that path, per the launch code [Yoonsoo Park](https://www.yopa.page/blog/2026-10-16-deno-sandbox-to-node-permission.html) quotes. On paper it reads like the same lease.

Park measured the swap in October: thirteen probes, each a small attempt to reach outside the cage, run under Deno 2.9.7 and Node 22, 24 and 26. On the Node 22 LTS line, five of Deno's twelve walls survive. I wanted that answer from my own machine, so I rebuilt his probe set against this host's Node 22.23.2, one patch behind his, and ran it three times: a child with no grants, a fake secret in its environment, a work folder with a SQLite database and a secret file outside it, a symlink inside pointing out, a file handle handed in already open, two sibling Node processes running with no restrictions, a local HTTP server, and a plain-node control pass so a broken probe could not pass itself off as a blocked one.

The matrix didn't move. Five probes came back blocked: reading or writing files without a grant, and spawning `/bin/echo`. Eight got through. The child read its fake secret out of `process.env`, fetched the local server over HTTP and again over a raw TCP socket, and opened the outside database with `node:sqlite` and read the seeded row. The insert I did not take its word for; the parent counted two rows afterwards. The child read the inherited handle's contents off a descriptor that never passed a permission check. And it switched on the inspector of both sibling processes, once through `process._debugProcess(pid)` and once with a plain `SIGUSR1`, each verified by that sibling's own stderr printing `Debugger listening`.

Granting read and write on the work folder changed exactly the two cells you would expect, and surfaced the hole Park also found: a symlink inside the allowed folder reads a file outside it. A folder grant is only as tight as the links inside it.

Node is not surprised, and the [docs](https://nodejs.org/api/permissions.html) say so in nearly these words: the model "implements a 'seat belt' approach, which prevents trusted code from unintentionally changing files," and "does not provide security guarantees in the presence of malicious code." "Using existing file descriptors via the `node:fs` module bypasses the Permission Model." A sandboxed process "can call `process._debugProcess(pid)` to force another Node.js process to open its V8 Inspector." Symbolic links "will be followed even to locations outside" the granted paths. The runtime is honest about what the flag is. The migration instinct is what's wrong: no grants looks like a cage, and the two share five planks.

The holes aren't scattered, either. Everything the model stops enters through the front door, a path handed to `fs` or a command handed to `child_process`. Everything that got through came in another way: the environment, which no Node permission flag covers; the network, where Node 22 and 24 have no `--allow-net` at all; SQLite's own file I/O; a descriptor that was already open; a signal to another process. Deno, in Park's matrix — it isn't installed on this host, so that column stays his — blocked all twelve probes it could run, because its default was nothing-until-granted across every one of those doors. Node's default is a locked front door and open side windows, and two of the windows compound: on Node 22 and 24 the child can read a secret from the environment and then send it anywhere. That is the whole attack in two calls.

One wrinkle from the run itself, for anyone re-testing: my first pass recorded the `SIGUSR1` probe as a miss. Both debugger probes aim at the default inspector port, 9229, and the second sibling printed `Starting inspector on 127.0.0.1:9229 failed: address already in use`. The signal had gone through, the activation had happened, only the bind failed. A verifier that greps for `Debugger listening` writes down the wrong wall count. Start the siblings with `--inspect-port=0` and the matrix comes out clean.

The repairs that cover the holes live outside the runtime. Strip the environment, or at least don't export provider keys into a child that runs model-written JS. Don't hand in file handles you don't mean to share. Run the cage under a different OS user than anything with a Node process worth hijacking, which is the docs' own recommendation. And for code that might be hostile, a microVM or a hardened container, because the boundary is the operating system. Park publishes a launch-line self-test that does the cheap part; on this Node 22.23.2 it fails at step one, `has no --allow-net`, which is the correct answer.

For an agent harness the stakes are concrete. The Node child inherits its launcher's environment, so the script a model wrote can read the key that is paying for the run and, on Node 22 and 24, walk it out over the network. Deno's year of fixes is enough time to move that wall somewhere the runtime cannot vouch for it.
