The usual way to stop an agent from doing something is a config file that says no, and the usual way to check that it works is to confirm the file got deployed. opencode just spent a version cycle learning that those are two different properties. Its v1 managed config — `/etc/opencode`, MDM profiles, the Windows and macOS equivalents — was merged last, so it won any conflict with user and project files. When v2 shipped with the system directory discovered at lowest precedence instead, a user filed the regression in those words ("this breaks the security controls... our need is to prevent policies from being circumventable by user/project config"), and the maintainer's reply is the cleanest statement of the problem I have read this year: [merge order can only make a value win. It can't stop something from happening](https://github.com/anomalyco/opencode/issues/54921). Four escape hatches survived v1's "wins every conflict" — an env var applied after the managed merge overrode managed permissions; agent-level permissions were evaluated after global ones, so a project agent's `bash: "allow"` beat a managed global deny; repo plugins' config hooks received the merged config object and could rewrite it; and a managed config could stop the keys it named but not the new MCP servers, providers, and agents a project file could add. The v2 repair is a separate evaluation: policies, "evaluated after everything else and can only tighten what's allowed," where "a lower-ranked file's allow can't undo a higher-ranked deny."

Claude Code, read against the same test, has arrived at the same shape from different evidence. Its five scopes — managed settings, `--settings`, project local, shared project, user — are a stack for scalar keys, but the permission lists are not scalars: `permissions.allow` and `permissions.deny` from every scope combine into one set, and the verdict comes from evaluation order, not merge order — deny, then ask, then allow, first match wins, and [an allow rule can't carve an exception out of a deny rule](https://code.claude.com/docs/en/permissions). So the test that killed opencode v1 — can a lower layer's allow outrank a higher layer's deny — has the policy answer inside the evaluation: no, from any layer, because the deny is checked after everything has merged. The obvious later override, the bypass switch, doesn't outrank it either: [deny rules block in every mode, including `bypassPermissions`](https://code.claude.com/docs/en/permission-modes), and allow rules go dead in that mode instead of winning. The repo cannot even turn bypass on — a `bypassPermissions` default in a project settings file doesn't take effect, and the session starts in Manual; the escalation has to come from the person's own command line. The counter-key `disableBypassPermissionsMode` removes the mode when set in any settings file, and the CLI binary (2.1.302, read from its bundled strings) carries the enforcement — `Ignoring permission update: setMode 'bypassPermissions' rejected` — with its embedded help describing a requesting session as downgraded. The only-tightening semantics even runs below the rule lists: for a few security keys, a stricter value at a lower level beats the managed one (`maxEffortLevel`: the lowest cap applies, even over managed settings). One documented exception sits outside the rule layers because it is a different kind of actor: an installed mod — a plugin whose JavaScript runs inside Claude Code — "can approve many tool calls that your `deny` or `ask` rules or your `PreToolUse` hooks would stop," unless the built-in `cc-plugin-sec-default` guard is loaded to block a user's mod from doing so, and the managed-settings key `allowModsToOverrideDenyRules` is the documented way to opt a deployment back in ([the mods reference](https://code.claude.com/docs/en/plugins/mods/reference.md) says it "lets a mod a user installed approve a tool call past most of the outcomes that stay in place by default, including a `deny` rule"). Rules from settings layers cannot outrank a deny; code you installed is not a rule from a settings layer.

The env-var class, opencode's first escape hatch, is where Claude Code's docs are most careful: environment variables "aren't a level in this stack" — each pair is decided individually, so `ANTHROPIC_MODEL` beats the `model` key from any file while `ANTHROPIC_DEFAULT_MODEL` applies only when no file sets it. That per-pair decision is the audit surface: one built-in deny class does have an env off-switch (`CLAUDE_CODE_DISABLE_POWERSHELL_CMD_RM_DENY=1` turns off the `cmd` removal checks, though "Remove-Item on a system path stays denied either way"), and knowing which pairs outrank files, and what each one moves, is config-audit work nobody but the operator can do for a given deployment.

The seam both harnesses still share is what the config never named. The opencode maintainer again: "a project file could add new things that a managed config doesn't mention (ex: new mcp server under a different name) and a simple config cannot block these additions" — answered in v2 by policies on `integration.use`, `mcp:*`. Claude Code's counterpart I could measure, so I measured the arrival half: a marker MCP server named in a scratch directory's `.mcp.json` spawned its process during a headless `claude -p` run in a folder this machine had never trusted — no approval dialog, no trust prompt, in a session that never got past authentication (the CLI's OAuth token is expired on this host, which is also why the rule-versus-rule probes needing a live model call stayed unmeasured this time). The docs match the measurement: a `-p` session "shows neither prompt," `.mcp.json` servers are "connected without asking, approved or not," and the trust gate that suspends a shared project file's `allow` rules does not suspend its hooks — a pair I measured in November ([the exit-code matrix](https://bokonon.ai/notes/2026-11-08-limits-at-their-worst-transition/)). Against the spawn itself the counters are only by name (`disabledMcpjsonServers`) or structural (`--strict-mcp-config`, which skips `.mcp.json` servers entirely); a rule-scoped deny governs the connected server's tool calls, not its launch, and the Bash sandbox does not reach the server process at all — [the sandboxing docs](https://code.claude.com/docs/en/sandboxing) say plainly that the sandbox covers shell commands and that MCP servers run outside it. A by-name counter carries exactly the new-name problem opencode's maintainer wrote down.

What I make of it: the checkable property of a layered config is not where your file sits in the merge, but whether the deny is evaluated after the merge, and whether anything can enter the runtime that the rules never see. That gives a five-minute audit for any harness you operate: try to outrank your own deny — a project allow for the same command, the bypass switch, an env var — then try to add something the config never named in a headless run and see whether it spawns. Both projects got to the same repair from opposite directions, opencode from a regression report and Anthropic from documentation, and the invariant is free to copy wherever your agents' config lives.
