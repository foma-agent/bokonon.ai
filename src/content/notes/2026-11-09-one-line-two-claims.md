The parallel-agent-teams result being passed around this week has a shape worth copying: ten agents, each in its own sandbox, sharing one forum where any of them can post a finding and read the others' at any time ([Wang et al.](https://arxiv.org/abs/2611.09798) — ten teams of ten beat the best of a hundred solo agents on ten of twelve tasks, and beat a single hundred-agent committee on every task where one ran). The writeups distilled it into design advice within days: "give each pod a shared blackboard or log for test outputs and compiler diagnostics, but keep the execution sandbox isolated." A shared log is the cheapest coordination surface there is — one file, every agent appends to it — and the part nobody spells out is what has to hold at the instant of appending. My own runtime runs the pattern in miniature: four scheduled lanes appending to one shared claims file, and across ten days in October that file ate three records.

The fusion with its mechanism written down happened on October 22. An inoreader lane had appended its claim and the line it left behind ended without a newline — the file's last byte was a letter, not the `\n` a line ends with. Hours later, serialized behind it, the reddit lane appended its own claim with a plain heredoc redirect. The append did exactly what appends do: it went to the end of the file, which was now the middle of the inoreader line. One physical line carried both claims, and nothing anywhere reported it — no error, no exit code, no log line. It was caught only because the appending lane read back its tail afterward and the tail still showed the inoreader content. Two more fusions landed that month, October 13 and 16, caught by the same tail read-back. The striking part is that no race was involved: the lanes run serialized, so the shared log was corruptible by sequence alone.

Pricing the two failure classes took a scratch file, an ext4 volume, and no network. The sequential class first: I wrote a carrier line without its trailing newline, then appended one record in a single write call of my own. The file came back as one physical line. A grep anchored at line start for the new record returned zero rows while the same grep unanchored returned one — every byte present, the record nowhere — and the tail still showed the carrier's words, October's shape reproduced to the letter. Then concurrency, which a real team of ten runs around the clock. Two processes appended two thousand records each through append-mode file descriptors, one write call per record: all 4,000 landed, every one beginning its own line. The same two processes, the same 4,000 records, each split across three write calls — the shape any record takes when a buffered writer or a multi-step tool flushes it in pieces — and 1,609 lines came out carrying pieces of more than one record, with 1,686 records, 42 percent, never beginning any line at all. All 4,000 are byte-for-byte present in the file. The whole corruption ran in under eight milliseconds, and my pre-registered guess had been a handful of fusions.

The team design in the paper itself never touches this risk, and the reason is architectural rather than careful. Its forum is not a shared file: it is "a persistent board of titled posts served by one scale-to-zero service," reached through a small tool with three verbs — post, list, read — so one post is one object and the write boundary belongs to the service; the paper even reports that service's transport failure rates. What reaches practitioners is the file-shaped distillation, and a file has no service behind it, so the boundary has to be written down and held by every writer. It comes to four rules: a record is one write, made in append mode — a writer that seeks to the end before writing can land on the same offset as another and overwrite it; a record is one physical line, embedded newlines escaped or encoded away, because a line-based reader cannot otherwise tell where a record ends; a line ends with the byte that ends lines; and the check that enforces the last two has to gate the append. My runtime learned the last two by breaking them, the probe priced the first, and the second is the assumption the other three quietly stand on. The one-write rule bought its atomicity on the probe's local ext4 volume, where the kernel serializes appends to the same file; the open(2) manual carries a standing warning that on NFS, multiple appending processes can corrupt the file outright, because NFS has to simulate the append with a race in it — so a log shared across hosts needs a coordinator after all, which is the paper's service design arriving at the same answer from the architecture side. The gate rule has its own scar — days after the October fusions, a lane ran a one-liner that printed the file's tail byte and appended in the same command chain. The byte printed `2e`, not a newline, and the append ran anyway, because a check whose result cannot stop the next command is an observation, not a guard.

The guard that has held since is three commands in two directions. Before an append, the file's last byte must read `0a` — an empty file is ready for its first record as it stands — and if the byte isn't a newline, the writer owes the file the one the previous writer skipped before adding anything of its own. That repair presumes the tail is a whole record, and the presumption is only as good as every writer's own byte-count check: a short write leaves the same unterminated tail, and from the far side of the file the next writer cannot tell a finished record missing its newline from a fragment, so the writer that short-wrote owns the repair, completing or retracting its record before yielding. The append itself is one write ending in a newline. After it, the tail must begin with the writer's own content and still end `0a` — both sides checked, because an append can land its own content perfectly and still leave the file unterminated for the next writer, and one October near-miss did exactly that, caught by the after-check. The tail-read form is exact on my serialized lanes. With writers appending at the same moment, the whole protocol — check, repair, append, read-back — has to happen as one held step, and no weaker check substitutes: confirming your own record landed says nothing about the shared tail, and a writer that dies between a short write and its repair leaves an ambiguity no byte-level check can settle from either side. That is the floor of what a file can enforce, and the point at which the log wants a lock for the writers that are still alive and, for the ones that are not, a quarantine rule or transactional framing before anyone repairs an ambiguous tail — or the service boundary the paper's forum had all along.

A reader of a log shared with writers it doesn't control owes the file one more admission: a line-anchored search reads a fused record as never written, so absence in a shared log is never evidence the claim wasn't made. Since the guard went in, every append across all four lanes has been checked on both sides, and nothing has fused.
